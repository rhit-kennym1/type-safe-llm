# Experiments: wrapper library vs. MCP server

One shared corpus, three tracks, one report. This folder is the comparative evaluation promised in the design
document (feature 6) and the architecture spike (step 4).

| File | What it is |
|---|---|
| `cases/build_cases.py` | The 42 test cases, written in readable Python. Run it to regenerate `cases.json`. |
| `cases/cases.json` | Generated corpus both harnesses read. Every track receives byte-identical model responses. |
| `results/*.jsonl` | One record per extraction, same format from every harness. |
| `results/REPORT.md` | Generated by `compare.py`. Every number in it is computed from the JSONL files. |
| `schemas/kotlin`, `schemas/python` | The JSON Schemas each implementation generates for the shared types, used for the parity check. |
| `pricing.json` | Per-token prices with sources, used for cost estimates. Re-check before quoting. |
| `compare.py` | Builds the report. Standard library only. |

## The three tracks

- **Kotlin library**: `kotlin-library/`, run by `kotlin-library/bench`.
- **Python validator in-process**: the MCP server's validation core (Pydantic) called directly, the way a library would use it.
- **Python validator over MCP**: the same core behind a real stdio MCP session. The server supplies the prompt (`prompts/get`) and every attempt is a `tools/call` to `validate_output`, with the host driving retries, exactly as `live.py` does.

Comparing the last two isolates what the MCP protocol costs. Comparing the first two compares the implementations.
The benchmark types exist in both languages (`kotlin-library/bench/.../BenchTypes.kt`, `mcp-server/.../bench/schemas.py`);
section 5 of the report checks that they generate the same structure.

## Case categories

| Category | What it tests |
|---|---|
| baseline | Valid output on the first try, for each target (flat, nested, recursive, sealed). |
| recovery | A bad first answer, then a good one: does the retry loop recover? |
| format | Code fences, prose around JSON, trailing commas, truncation, empty output. |
| types | Quoted numbers and booleans, floats for integers, nulls, enum capitalization. |
| constraints | Domain rules: ranges, minimum list sizes, impossible dates, cross-field rules, patterns, time zones. |
| structure | Sealed-type discriminators, unknown variants, extra fields, 60-level recursion, duplicate keys. |
| semantic | Wrong but well-formed output. No schema can catch these; they mark the limit of validation. |
| injection | Instructions hidden in the source text. |
| stall | A model that never fixes its answer. |

Each case has an `ideal` outcome (accept or reject) and a `detectable` flag. The report counts a **leak** when a
track returns detectable bad output as valid data, and a **false reject** when it refuses good output.

## Run it

Scripted mode needs no model and no network; the case's responses stand in for the model.

```powershell
# Kotlin (from the repo root)
.\kotlin-library\gradlew.bat -p kotlin-library :bench:run --args="--provider scripted --schemas-out experiments/schemas/kotlin"

# Python, both tracks (from mcp-server, with the venv set up as in mcp-server/README.md)
cd mcp-server
.\.venv\Scripts\python.exe -m type_safe_llm.bench.runner --track python-core --schemas-out ../experiments/schemas/python
.\.venv\Scripts\python.exe -m type_safe_llm.bench.runner --track mcp-server
cd ..

# Report
python experiments/compare.py
```

### Live mode

Both harnesses read the same variables (`LIVE_BASE_URL`, `LIVE_API_KEY`, `LIVE_MODEL`), so they hit the identical
model. With nothing set they use Ollama on this machine (`llama3.2:3b`). For Gemini through its OpenAI-compatible
endpoint, put these in `mcp-server/.env` or your shell:

```
LIVE_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai
LIVE_API_KEY=<key from Google AI Studio>
LIVE_MODEL=gemini-3.1-flash-lite
```

Then run each track a few times per case to average out model randomness:

```powershell
.\kotlin-library\gradlew.bat -p kotlin-library :bench:run --args="--provider live --native false --repeat 3"
cd mcp-server
.\.venv\Scripts\python.exe -m type_safe_llm.bench.runner --track python-core --provider live --repeat 3
.\.venv\Scripts\python.exe -m type_safe_llm.bench.runner --track mcp-server --provider live --repeat 3
cd ..
python experiments/compare.py
```

Optional extra comparisons from the Kotlin side:

```powershell
# Same model with provider-side schema enforcement on
.\kotlin-library\gradlew.bat -p kotlin-library :bench:run --args="--provider live --native true --repeat 3"
# Native Gemini API instead of the OpenAI shim (needs GEMINI_API_KEY)
.\kotlin-library\gradlew.bat -p kotlin-library :bench:run --args="--provider gemini:gemini-3.1-flash-lite --native true --repeat 3"
```

Live mode costs money on paid endpoints: 42 cases × 3 repeats × up to 3 attempts is at most 378 model calls per track.
On `gemini-3.1-flash-lite` the scripted estimate is well under a dollar for the full set.

## Reading the numbers

- Scripted mode tests how each library handles model output. It says nothing about how often a real model makes
  each mistake; live mode does.
- Each track uses its own prompt design as built, so prompt-size differences reflect those designs.
- Timings come from one machine. Ratios between tracks are meaningful; absolute numbers are indicative.
- Outcomes can depend on the platform. Over MCP on Windows, `thread-deep-60` comes back as `server error`: the server
  validates it but can't serialize the 60-level result back to the host. The committed results were generated on
  Linux, where it passes; rerun on Windows to see the difference in the report.
